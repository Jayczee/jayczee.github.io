SublinkPro：把零散节点整理成自己的订阅
2026-04-27
2026-09-09
网络与服务
/
代理配置

最近发现个很有趣的项目，SublinkPro。

手里的节点慢慢多了起来，有自己搭的，也有从各个地方入手的。有些直接给节点链接，有些给一整条订阅，还顺带附上供应商自己的分流规则。

一个两个的时候，复制进客户端就完事了。再多一点，就开始乱：节点名字各写各的，几个订阅里都有“香港 01”，自建节点又单独放在另一份配置里。想换个规则，还得挨个改。

SublinkPro 正好能把这些东西收在一起。我在服务器上搭了一套，节点、来源和规则模板都放进去管理，最后给客户端一条自己整理过的订阅。供应商负责提供节点，日常用什么名字、选哪些节点、套什么规则，由自己决定。

先分清：导进来的订阅，和发出去的订阅#

左侧“订阅管理”下面放了好几个页面，刚开始容易把“机场管理”和“订阅列表”看混，因为两边都在说订阅。

这里其实有个方向上的区别。机场管理接收的是供应商给你的订阅，负责拉取和更新节点；订阅列表里创建的是你给客户端用的订阅，决定把哪些节点和哪份配置发出去。

平时主要在这几处来回切换：

页面用来做什么
机场管理导入外部订阅，管理上游更新和用量信息
节点管理看所有节点，修改备注、分组、来源，检查节点状态
节点检测检查节点的延迟、速度等状态，供筛选时参考
订阅列表选择节点和模板，生成自己要用的订阅
模板管理保存 Clash、Surge 等客户端使用的配置模板
标签管理整理节点标签，方便后续筛选和选择节点

整个过程大致是这样：

外部订阅里原本带了什么策略组，不一定要照单全收。把节点整理好，再套自己的模板，配置才不会跟着供应商的习惯来回变。

节点管理：先把名字和分组收拾好#

这张图里，自建的新加坡节点和外部订阅的香港节点已经放在同一张表里了。协议、分组、来源、国家、延迟、速度都能直接看到，不用再打开几份配置对着找。

来源和分组最好分开用。 来源记“这个节点从哪来”，分组记“我准备怎么组织它”。比如来源可以是“SG-自建”或某个供应商，分组可以是 SG-self、HK-backup。名字不用很讲究，过一个月自己还能看懂就行。

节点备注也一样。与其留着一排“香港 01”，不如加上来源或用途。列表里还能看到原始名称，回头核对上游节点时不至于对不上。

节点多了之后，先筛选再批量操作会省事一些。图里支持按分组、来源、协议、国家、标签筛选，也能设置最大延迟、最低速度等条件。筛完勾选，就可以批量修改分组、来源、国家和标签。

延迟低，不代表下载就快#

拿图里的三条自建节点来说，AnyTLS 那条显示约 31ms，延迟比旁边两条低，但下载速度只有约 4.09MB/s；VLESS 那条约 55ms，下载速度却到了 54MB/s。

所以不能只挑最绿、数字最小的那一个。日常交互和大文件下载看重的东西不完全一样，而且这只是当时的测试结果，不能据此给几个协议排高低。

还有一点：面板部署在服务器上，面板的测试结果反映的是服务器那边的网络条件。 自己电脑到节点的线路可能完全不同。可以先用它排掉明显有问题的节点，最后还是要在实际使用的客户端里试。

右边的原生 IP、机房 IP、欺诈评分也是参考信息。“原生 IP”和“住宅 IP”不是一回事，截图中的节点就可以同时显示“原生 IP”和“机房 IP”。评分来自检测服务，也不是某个网站一定能用、一定不会弹验证的保证。

模板：把常用配置留一份自己的#

模板可以理解成客户端配置的底稿。端口、DNS、策略组、分流规则这些内容放在这里，生成订阅时再配上选好的节点。

第一次用，没必要从空白 YAML 开始写。可以先选一份现成规则，生成配置，确认能在客户端里加载，再逐步改成自己的习惯。比如文件名就叫 daily-clash.yaml，以后在订阅页面选它。

截图里有远程规则入口，也有“规则生成/转换”和编辑器。远程规则拉不下来时，再考虑“使用代理下载远程规则”。这个开关管的是下载规则时走不走代理，不是把客户端的所有流量都切成代理。

Include-All 这个开关要留意#

截图里的开关是打开的，但下面的说明同时写着“关闭（推荐）”。它们的区别是：

设置节点怎么放进策略组
开启 Include-All使用客户端的 include-all 匹配节点，不遵循 SublinkPro 的系统排序
关闭 Include-All由 SublinkPro 按顺序插入节点，遵循系统的排序和过滤规则

如果已经在面板里认真排了节点顺序，希望生成的配置也照着来，可以先关掉它。想用 include-all，则要确认客户端内核支持，不能只看配置文件能不能下载。

也别把截图里编辑器的前几行抄下来当完整模板。下面还有策略组和规则没有展示，直接用截出来的一小段，肯定不够。

创建订阅：选好节点，再选模板#

节点和模板准备好之后，再来创建订阅就比较直观了。

先起个能分清用途的名字，比如“日常使用”，再选择对应模板。图里能分别选 Clash 和 Surge 模板；要用哪种客户端，就先把那种格式配好。模板不是随便换个后缀就能通用，节点协议也得是客户端支持的。

节点选择有三种方式：

方式适合什么情况
手动选择节点只想固定用几条，自己勾选最直接
动态选择分组希望订阅跟随某个分组里的节点变化
混合模式固定留几条节点，同时带上动态分组

截图当前选的是手动模式：左边筛选、勾选节点，添加到右边的“已选节点”。这种方式不会因为分组里后来多了节点，就自动把新节点加进来。

如果用的是经常更新的外部订阅，动态分组通常更省心。分组里的节点增减后，重新生成或拉取订阅时会按当时的分组内容选择；客户端已经下载到本地的那份配置，仍然需要更新才会跟上。

上面几个选项也不用见框就勾：

  • 更新间隔：截图说明写的是填 0 默认一天，并且受客户端支持情况影响。这是输出给客户端的更新参数，和上游订阅在服务器上的拉取周期要分开看。
  • 强制开启 UDP：确实需要 UDP 时再开，节点和客户端本身也得支持。
  • 跳过证书验证：正常情况下保持关闭，不要把它当成“连不上就试试”的通用修复。
  • 替换服务器地址为 Host：涉及地址与 Host 的处理，没有明确需求可以先不动。
  • 实时获取用量信息：依赖上游是否提供用量信息。手动添加的自建节点，不会因此就自动出现套餐剩余流量。

先保持简单，能正确导入、选节点、访问，再加别的设置，排查起来也容易些。

拿这批节点配一条日常订阅#

假设现在有截图里的几条新加坡自建节点，再加一批外部订阅的香港节点，可以这样整理：

  1. 自建节点放进 SG-self，来源记为“SG-自建”。外部节点保留供应商来源，把准备日常使用的香港节点放进一个单独分组。
  2. 在节点管理里检查可用性，把明显失效的节点处理掉。速度暂时没测过的，不要直接当成慢节点删掉。
  3. 新建 daily-clash.yaml 模板，先用现成分流规则，关闭 Include-All，保留自己需要的策略组。
  4. 新建“日常使用”订阅，选择这个模板。想让两组节点都跟着分组变化，就用动态分组；想固定几条自建节点，再带上外部节点分组，就用混合模式。
  5. 保存后，把对应客户端格式的订阅链接导入客户端。更新一次，看看节点是否齐全、策略组是否正常，再分别试一下自建和外部节点。

这里还有个区别：SublinkPro 里的分组是用来整理、选择节点的，不等于客户端里一定会自动出现一个同名策略组。客户端上看到的分组怎么命名、怎么选节点，还得看模板。

这样处理后，上游更新节点、自己调整备注，主要在 SublinkPro 里完成。客户端继续用这条整理好的订阅，不用每次都把几个来源重新拼一遍。

链式代理可以后面再折腾#

原先看上这个项目，还有一个原因就是它支持链式代理。节点列表里能看到“修改前置代理”，项目文档也提供了订阅级的链式配置。

在项目的 Clash 链式配置中，这类关系会通过 dialer-proxy 写入生成的配置，由支持它的客户端内核执行。不是把 SublinkPro 面板搭在哪里，所有流量就会自动经过哪里。

多经过一跳不保证更快，A 到 B 的线路同样重要。先让普通订阅跑通，有明确的入口、出口需求时再加链式配置就好。具体操作可以看项目的链式代理说明。

部署之后，记得留住数据#

部署方式直接参考项目的 Docker Compose 安装说明。比起容器本身，更需要留意挂载出来的 db 和 template 目录：节点、订阅配置和模板都在这些持久化数据里，升级、换机器时要一起保留。

第一次登录后改掉默认密码。如果把面板放到公网，配好 HTTPS；生成的订阅链接也别贴到公开的地方，它里面可能就带着访问凭据。

对我这种节点来源比较杂的情况，SublinkPro 最省事的地方，就是终于有个地方把它们统一收拾了。刚开始先用好节点、模板、订阅这几块就够了，没必要为了用上全部功能，把一条日常订阅配得越来越复杂。
