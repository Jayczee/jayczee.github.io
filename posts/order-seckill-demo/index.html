2026 年 9 月 15 日更新：补充可运行的 order-seckill-demo、真实 MySQL / Redis 实验和压测记录。依赖与镜像版本固定在源码中，文中的数据来自本次实验。

上一篇订单实验解决了重复下单、超卖、支付取消和异步补偿。继续往下想：如果同一秒来了几千个请求，都要买同一件商品，会怎么样？

条件扣库存的 SQL 仍然可以保证不卖成负数。可请求可能先堵在连接池、锁等待或者 HTTP 线程上。账是对的，用户却一直转圈。

这次沿用上一篇的业务模型，做一个独立的 order-seckill-demo。原来用内存模拟的数据库换成真实 MySQL，再逐步加入 Redis。先测普通下单，再看每一次改动到底解决了什么。

一、先说清楚秒杀要做成什么样#

假设一场活动只有 100 件商品，每人限购一件。开售时请求集中涌入，大多数人最终买不到。

接口至少要回答这几件事：

  • 还没到开售时间，不能提前占库存。
  • 同一个人连续点十次，只能得到一个购买结果。
  • 库存不能卖成负数，付款和取消不能同时成功。
  • 服务忙不过来时，明确拒绝或排队，不能无限等待。
  • 已经告诉用户“受理了”的请求，后面要能查到结果，也要能恢复处理。

这里的 QPS 就是每秒处理的请求数。但“处理”指哪一步，必须说明白：

数字含义
请求到达量一秒内有多少次抢购请求要发过来
接口响应量一秒内返回多少次结果，可能包含售罄、限流和失败
受理量一秒内有多少人拿到排队资格
落单量一秒内真正向 MySQL 写入多少笔订单

库存瞬间卖完后，接口只返回“售罄”，QPS 很容易好看。这不代表系统能每秒创建同样多的订单。后面的正确性实验用 100 件库存；比较落单性能时另外准备充足库存，避免把售罄响应算成成绩。

本例还有两条明确规则：取消或超时后，同一个用户不能再次参加这场活动；付款时间从订单创建时开始计算。规则不同，幂等记录和库存释放方式也得跟着改。

3.3 账对了，不代表能无限并发#

大家抢同一个活动，条件更新最终还是争抢同一行库存。前一个事务没有结束，后一个就可能等待。连接池只有有限连接，HTTP 线程也有限。

把连接池从 8 改成 800，不会让一行库存同时由 800 个事务随意修改，反而可能让数据库承担更多等待。

本例每个应用最多 8 个数据库连接、64 个 HTTP 工作线程。下一步先测它能稳定处理多少，再决定放多少请求进来。

四、第一道改动：忙不过来就明确限流#

限流的意思是：在一个时间范围内，只允许有限数量的请求继续处理。它保护后面的服务，不负责增加库存，也不负责让更多用户中奖。

INCR 是加一，EXPIRE 是给计数器设置过期时间。把它们放在同一段 Lua 脚本里，避免加一之后进程退出，计数器却没有设置过期。

两个应用实例用同一个计数器。超过阈值返回 HTTP 429 和 LIMITED，不再进入订单事务。用户没拿到资格，可以稍后重试。

这次创建独立的限流活动，只放一人每窗口通过，便于手动观察：

两条请求在同一个一秒窗口里到达时，第二条会返回 LIMITED。限流阶段先过限流再查原订单，所以已下单用户重试也可能暂时收到 429；他仍然可以通过查询接口查看已有订单。

这里是一个从首次请求开始计时的固定窗口，不是平滑发放令牌。窗口切换附近仍可能有突刺。生产系统还可以按用户、活动、IP 分层限制，但不能只按 IP 判断用户，否则公司网络里的很多人可能共用一个出口。

阈值要从实际容量倒推。 首轮实验里，数据库实际落单约百单/秒，我却先把阈值设成 200。结果限流没有明显保护住延迟：200 依然高于这套环境的处理能力。后续对照将阈值降到 80，给正常波动留出空间。

单在 Java 代码里限流，仍要先占用 HTTP 连接和线程。更外层的入口限流、页面静态化、请求大小和连接数限制也有价值。本 Demo 先把业务入口这一步测清楚。

五、第二道改动：没抢到的人，不必都去查 MySQL#

只有 100 件库存，却有很多人请求。对大多数落选请求，先占一个数据库连接，再执行库存更新，代价太高。

可以在活动开始前，把可售数量放进 Redis。抢购先检查 Redis，有资格的人才进入后面的落单流程。

这份数量称为预占库存：从 Redis 扣一件，表示先留出一个购买名额；正式订单还没有写入 MySQL。

5.1 为什么不能只写一个 DECR#

DECR 的确能原子减一，但业务不止一个动作：

  1. 这个用户之前有没有抢过？
  2. 活动开始了吗，结束了吗？
  3. 还有库存吗？
  4. 当前请求量、排队量有没有超过上限？
  5. 为用户保留名额，并记录后面要处理的任务。

这些操作如果拆成几次 Redis 请求，其他请求可以插在中间。两次点击可能同时通过“没抢过”的判断。

因此把它们放进 reserve.lua，让 Redis 连续执行完再处理其他命令。每场活动有这些数据：

数据保存什么
活动 Hash剩余预占库存、时间、限流阈值、积压数量
用户 Hash用户 ID → 第一次受理的请求 ID
限流计数器当前窗口的请求数
Stream需要异步创建订单的任务

Hash 可以先理解为 Redis 里的键值表。用户再次请求时，直接返回第一次的请求 ID，不再次扣库存。

同一个活动只使用一个阶段。创建为 sync 的活动不能从 async 入口抢购，避免绕过 Redis 修改同一份库存。

5.2 预占后，任务放在哪里#

如果先减 Redis，再向一个独立消息队列发消息，两步之间进程退出，就可能留下“库存少了，任务没了”的名额。

这里需要的是 消息队列（Message Queue，简称 MQ）：入口把“替这个用户创建订单”写成一条消息，后台程序稍后读取并执行。RabbitMQ、RocketMQ、Kafka 都能承接这类异步消息，但消息组织、确认和重试方式有所不同。

本 Demo 使用 Redis 自带的 Stream 承担消息队列功能，没有另外部署上述独立中间件。可以先把 Stream 理解为一张不断追加的待办列表，每条任务有唯一消息 ID，消费者可以读取、确认，也能找到尚未确认的任务。它不是普通 Redis 缓存，也不是应用进程里的 @Async 内存队列。

但 Lua 不是 MySQL 事务，执行中遇到错误不会自动撤销之前的写入。本例由程序建立固定的键结构，不允许人工把 Hash 改成别的类型；内存耗尽、Redis 崩溃等故障仍然需要单独处理，不能因为使用 Lua 就宣称绝不丢数据。

本例所有键使用相同的 {seckill} 标签，使脚本涉及的键处于同一个 Redis Cluster 槽。它仍是一个热点，不是把 Redis 横向扩容的问题也顺手解决了。

六、第三道改动：用消息队列削峰，后台慢慢落单#

现在的请求链路分成两段。用户等的是上半段的受理响应，下半段仍然需要时间：

6.1 MQ 的“削峰填谷”，削掉的是什么#

假设数据库能稳定处理约 100 单/秒，一阵流量却让入口每秒受理 600 个资格，持续 5 秒。如果全都同步写库，多出来的请求就堵在 HTTP 线程和数据库连接上。

加入消息队列后，这些任务先排在队列里，消费者按数据库能承受的节奏处理。突发期间消化一部分，流量回落后继续处理剩下的，这就是削峰填谷。

用理想化数字算一次，不考虑启动和调度开销：

时间新进入队列消费并落单还在排队
第 1 秒结束600100500
第 5 秒结束累计 3000累计 5002500
接下来没有新请求0继续约 100 / 秒约 25 秒后排空

高峰没有直接压到数据库上，而是变成了后面一段时间的任务处理。第十节实测中“5 秒受理 3000 次，约 31 秒全部落单”，就是这个过程。这里说的是库存充足的性能实验；只有 100 件库存的真实抢购，预占最多只放行 100 个名额。

限流与削峰是两件事，需要配合使用：

手段决定什么用户看到什么
入口限流现在允许多少请求继续进入超额请求明确被拒绝，可按规则重试
MQ 削峰已经受理的任务什么时候处理先排队，再查询最终结果
消费速度控制每秒或同时允许多少任务写数据库避免消费者又把数据库打满
积压上限队列还能接受多少待办队列满时停止继续受理

MQ 不会自动知道数据库能扛多少 QPS。消费者开得太多，仍然可能把库打满；生产速度长期超过消费速度，队列迟早会满。需要结合消费并发数、处理速率、积压量和最老消息等待时间来控制。

6.3 消费者究竟是什么#

消费者就是后台执行任务的程序。本例写在 Worker.java 中，随 Java 应用一起运行；两个实例加入同一个消费组 orders。

消费组会把新任务分给其中一个消费者，并记录“发给谁了、有没有确认”。正常情况下不会让两个消费者都处理每条新任务，但故障恢复可能重复投递。

读取任务后，消费者调用的仍然是 Orders.create()：唯一约束、条件扣库存和订单创建仍由 MySQL 事务兜底。Redis 已经检查过库存，也不能删掉数据库里的保护条件。

本例每次读取最多 20 条，逐条执行事务，处理一轮后再等 50 毫秒。这是容易观察的教学实现，不是批量写入的极限性能实现。

这也不是严格的“每秒 100 条”配置：实际速度取决于每笔事务耗时。需要严格限速时，可以在消费者执行前加令牌桶；需要控制并发时，限制工作线程和同时处理的任务数。两个实例各限 100 / 秒，总量可能是 200 / 秒，要明确限制的是单实例还是整个消费组。

6.4 为什么队列一定要有上限#

如果一秒受理 600 个，而后台一秒只能落 100 单，每秒就多积压约 500 个。

队列把“接口等待”变成了“后台等待”，没有消灭等待。消费者永久跟不上，用户排队时间会越来越长。

所以活动设置 maxBacklog。脚本预占前检查未完成任务数，达到上限就返回 BUSY，这次不扣库存。任务真正落库并确认后，才减少积压计数。

验证脚本暂停消费者后，让 20 人抢 20 件库存，但队列上限设为 5。预期只有 5 人被受理，另外 15 人收到 BUSY；恢复消费后生成 5 笔订单。库存足够，也不意味着应该继续无限受理。

还要从用户能接受的等待时间倒推队列长度。例如稳定消费约 100 单/秒，希望排队大致不超过 5 秒，就不应随手允许积压几万条。100 × 5 = 500 只能作为粗略起点，还要为事务波动、失败重试留余量，并监测真实排队时间。

6.5 如果换成 RabbitMQ 或 RocketMQ，哪些地方会变#

目前的 Stream 已经实现了异步排队和削峰。独立消息中间件值得单独引入的场景包括：希望消息存储与 Redis 库存隔离、由独立消费者部署处理订单，或需要更完整的消息路由、重试和运维能力。选型要看具体需求，并不是把产品名字换掉就自然更快。

以 RabbitMQ 为例，对应关系是：

本 Demo换成 RabbitMQ 后
Lua 中 XADD 记录落单任务生产者向交换机发送消息，路由到订单队列
Stream 消费组读取任务消费者订阅队列
MySQL 提交后 XACKMySQL 提交后手动 ACK
pending 超时认领未确认消息在消费者连接关闭等情况下重新投递
五次失败后人工检查设计有上限的重试和死信处理流程

RabbitMQ 的 prefetch 可以限制消费者持有的未确认消息数量，帮助控制同时处理的工作量，它不等于每秒消费条数限制。生产者确认则用于判断消息是否被 broker 接受，不代表消费者已经创建订单；还要处理无法路由的消息，并按需求配置持久化、复制和队列类型。

最容易忽略的变化，是 Redis 与独立 MQ 不能再放进同一段 Lua：

发送超时可能是消息没到，也可能是确认响应丢了，不能直接归还库存。一个衔接办法是保留“Lua 预占 + Stream 待发送记录”，由转发程序把任务发送到独立 MQ，确认后再确认 Stream 记录。这样进程退出后还有记录可继续发送，但转发可能重复，最终落单仍然必须幂等。

另一种做法是调整受理模型，将受理记录和待发送消息写入同一个数据库事务，再用 outbox 转发。代价是入口重新承担数据库写入，不能宣称原来的纯 Redis 受理性能保持不变。

这些是扩展设计，本次源码和压测使用的仍然是 Redis Stream，没有拿它的数据当作 RabbitMQ、RocketMQ 或 Kafka 的性能结果。无论选择哪一种，下面的重复消费、提交后未确认、库存补偿问题都还在。

七、坑开始转移：任务会重复，进程也会退出#

7.1 数据库提交了，消息还没确认#

消费者正常顺序是：

XACK 告诉消费组这条任务已经完成。如果在提交后、确认前退出，数据库里已经有订单，Redis 却还认为这条消息没处理完。

这正是验证脚本里的 crash-after-commit 故障：真实退出一个 Java 进程，由 Compose 自动重启。

另一个实例随后认领空闲超过 3 秒的未确认任务，再次执行下单。唯一索引让它读到原订单，不重复扣库存，之后补上确认。

这叫 至少一次处理：任务可能处理多次，但业务副作用必须幂等。把 XACK 放在数据库提交前面更危险——确认后进程退出，没写完的订单可能再也没有人处理。

积压计数也得幂等。ack.lua 用消息 ID 记录是否已经扣过计数，重复确认不能把 backlog 减成负数。

7.2 不能只读新消息#

Stream 的未确认任务保存在 pending 列表中。如果消费者只读取新任务，进程退出前领到的那批任务可能一直躺在那里。

Worker.recover() 会扫描 pending，认领空闲超过阈值的消息。3 秒只是本实验的取值，实际任务很慢时也可能被误认领，所以数据库幂等不能省。

7.3 一直处理失败，要怎么办#

测试里的 fail 开关会让指定活动的消费持续失败。失败记录保存在 MySQL，包括消息 ID、活动、尝试次数和错误类型。

达到五次后，任务进入人工检查状态，保留 pending 和预占名额，不再自动执行业务。移除故障，再调用活动的 retry 管理接口，才恢复尝试。

不能一见异常就归还名额。异常也可能发生在“数据库提交成功，确认消息失败”的位置。这时直接加库存，会把已经生成的订单对应的库存再卖一次。

状态不确定时，先查原订单、恢复同一条任务。只有明确失败且没有正式占用库存时，才安排补偿。

八、用户不付款，库存怎样归还#

8.1 先在 MySQL 决定谁赢#

支付、主动取消、超时取消都可能同时碰到一笔订单。

Orders.finish() 先用 SELECT ... FOR UPDATE 锁住订单行，再检查它是否仍为 UNPAID。只有待付款订单才能继续流转；其他请求读到终态就直接返回。

支付接口也检查付款截止时间，不只是依赖每秒执行的超时任务。否则订单已经过期、定时任务还没扫到时，可能仍然付款成功。

这里的支付只是状态模拟。真实支付平台的异步回调、验签、金额核对和退款是另一层问题，不能用一个“支付按钮”替代。

8.2 MySQL 归还了，Redis 更新失败呢#

取消异步订单时，MySQL 的可用库存加一，Redis 预占库存也应加一。它们不在同一个事务里。

本例在取消订单的 MySQL 事务中，顺便插入一条 release_outbox。这个表可以理解为“还没办完的 Redis 回补待办”：

后台单独读取待办，执行 release.lua，成功后才把待办标记为已发送。Redis 暂时不可用，就留到下次继续尝试。

如果 Redis 已经加一，标记已发送之前进程退出，下次又会重做。因此 Lua 使用订单 ID 去重，同一订单只能回补一次。

验证脚本也真实退出了一次这样的进程：crash-after-release。恢复后两份库存都只归还一件，不是两件。

十、性能到底变好了多少#

压测使用充足库存，三个阶段都从统一的 Nginx 入口进入：

每档持续发请求 5 秒，每组重复两次，再等待本组队列处理完。限流阶段阈值默认 80，其余阶段的限流阈值调高，专门观察同步与异步路径的差别。

脚本按预定时间发请求，而不是“上一个返回再发下一个”。客户端最多 128 个未完成请求，超出后记录为 clientDropped。这些请求没有真正进入服务，必须单列，不能假装目标 QPS 全部达到了。

P95 表示 95% 的请求不超过这个耗时；P99 看更靠后的慢请求。异步阶段的接口延迟只代表受理速度，正式订单是否完成还要看积压和排空时间。

环境是 Linux x86_64，Java 17.0.20。两个应用各限制 1 CPU、448 MiB 内存；MySQL 限制 1 CPU、640 MiB；Redis 限制 1 CPU、256 MiB。压测程序、Nginx 和这些容器在同一台有其他工作负载的服务器上。这是受限环境下的对照实验，不是独占机器的容量认证，也没有实测“万人同秒”。

10.1 目标每秒 600 个请求，实际发生了什么#

每组计划发送 3000 次，表中范围来自两次完整运行，没有只挑最好的一次：

阶段实际发到服务的请求数接口 P95最终订单数响应全部结束时的积压
同步下单635～643955～975 ms635～6430
同步 + 限流 803000408～426 ms4000
Redis 预占 + 异步30006.52～19.24 ms30002516～2554

同步阶段有 2357～2365 次请求在压测客户端就因并发上限被丢弃，没有进入服务。不能说服务接住了全部 3000 次，也不能说它们全是服务端报错。发出去的请求虽然最终成功，但 P99 已到约 960～983 ms；把客户端排队也算上，计划发起到响应的 P99 是约 1.28～1.32 秒。

限流阶段处理了全部请求，其中 400 次落单、2600 次明确返回 LIMITED，相当于把落单保持在约 80 单/秒。它的代价是主动拒绝部分用户，并没有提高成功落单量。

这里还暴露了固定窗口的缺点：很多请求在窗口开始时一起通过，仍然有短时排队。仅看成功落单请求，P95 约 647～669 ms，比包含大量快速 429 的总体 P95 更高。下一步如果要继续压低尾延迟，应做平滑限流或限制同时执行的事务数，而不是只把阈值再调大。

异步阶段 3000 次请求全部被受理，约 5 秒收完响应；但当时还有约 2500 条任务没有完成。直到实验开始后的 30.86～31.55 秒，才生成全部 3000 笔订单、排空队列并通过对账，整体约 95～97 单/秒。

所以“受理约 600 QPS”和“落单约 100 单/秒”在这里同时成立。它适合缓冲一阵突发流量，不能无限维持每秒多进 500 条任务。

十一、离正式秒杀还有哪些距离#

这个 Demo 验证了两实例下的库存与恢复流程，但没有把单机实验包装成生产系统：

  • Redis 使用单实例和 AOF everysec，异常宕机仍可能丢失最近约一秒的写入。MySQL 的条件扣减能兜住正式库存，却不能替 Redis 找回全部已受理但尚未落库的请求。
  • Redis 不可用时不会自动绕过预占去直写 MySQL。未知状态下切换两套入口，容易把原来的限制全部绕开。
  • 本例 Stream、幂等集合和历史活动不会自动裁剪。长期运行必须按活动归档，确认任务和补偿全部结束后再清理，不能按固定长度随手删未确认消息。
  • Lua、同一个活动的库存行都有热点。加 Java 实例不等于数据库和 Redis 可以线性扩容；库存分桶还要处理配额浪费、补货和对账。
  • 页面静态化、CDN、登录、机器人识别、验证码、真实支付和消息高可用没有混进第一版。应在具体问题出现时逐层补齐。

秒杀的关键不是“多加了 Redis 和队列”。是让无资格的请求尽早结束，让有限的资格有地方等待，让已经受理的请求即使重复或中断也能处理到一个确定结果。
