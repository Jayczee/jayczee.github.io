最近我开通了 OpenCode Go，想把里面的 DeepSeek Flash 接到自己的 new-api，再给 ChatGPT Desktop 里的 Codex Agent 使用。

刚开始看起来很顺利：配好地址和密钥，问一句话，模型能正常回答。我以为这就算接完了。

真正让它干活时，问题才出来。只要涉及读文件、执行命令、搜索代码或修改文件，对话就可能突然中断。有时它还会直接回复这样一大段奇怪文字：

~~~text
<｜｜DSML｜｜ calls>
<｜｜DSML｜｜ invoke name="exec">
<｜｜DSML｜｜ parameter name="input" string="true">
...
</｜｜DSML｜｜ parameter>
</｜｜DSML｜｜ invoke>
</｜｜DSML｜｜ calls>
~~~

这些东西不是模型想对用户说的话，而是它准备发给客户端的“工具调用指令”。正常情况下，我们不应该看到它。

为什么普通聊天没问题，一干活就坏了？这要从 Agent 是怎么工作的说起。

> 标题里写的 ChatGPT Desktop 是我平时对桌面端的称呼。这次实际测试的是其中的 Codex Agent，请求走 `/v1/responses`，不是常见的 `/v1/chat/completions`。

## 聊天和使用工具是两回事

普通聊天很简单：

~~~text
用户提问 → 模型生成文字 → 客户端显示文字
~~~

但 Agent 要执行命令时，中间多了好几步：

~~~text
用户说“帮我看看项目里有哪些文件”
    ↓
模型决定调用 exec 工具
    ↓
客户端收到结构化的调用指令
    ↓
客户端在电脑上执行命令
    ↓
客户端把命令结果发回模型
    ↓
模型读完结果后继续回答
~~~

模型不能只在文字里说“请执行 `ls`”，而是要用客户端认得的固定格式，告诉客户端：调用哪个工具、传入什么参数、这次调用的编号是什么。

如果只是文字聊天，中转服务能把文字送过去再送回来就够了。要使用工具，则要求整条链路都听得懂同一套“暗号”。

## 我的请求经过了哪些服务

这次的实际链路是：

~~~text
ChatGPT Desktop 中的 Codex Agent
    ↓
nginx
    ↓
协议桥接程序
    ↓
new-api
    ↓
OpenCode Go 的 DeepSeek Flash
~~~

new-api 负责验证密钥、记录用量、选择渠道和映射模型名。但映射模型名只是“把信送到正确的收件人”，并不会自动翻译信里的内容。

客户端和 DeepSeek Flash 对工具调用的表达方式并不完全一样。new-api 能把请求发给上游，也能把回复发回客户端，但不一定能理解每种 Agent 工具格式。所以我在 new-api 前面加了一个很小的桥接程序，专门负责“翻译”。

## 第一个问题：工具指令被当成聊天内容

前面那段 `<｜｜DSML｜｜ calls>` 就是这种情况。

模型的真实意思是：“我要调用 `exec` 工具，参数是这段命令。”可中间层没有把它还原成客户端认识的指令，而是当成普通回答显示在界面上。客户端看到的只是一串字，当然不会真的执行命令。

桥接程序现在会检查这种 DSML 内容。它会读出工具名和参数，删掉界面上不该出现的 DSML 文字，再重新组装成客户端能识别的工具调用。

这里有个小麻烦：模型的回答是一点一点流出来的，一段 DSML 可能被拆成几块。如果看到一半就开始转换，参数会被截断。所以桥接会先暂存这部分文字，等收到完整结尾再处理。

## 第二个问题：双方对“工具”的定义不一样

桌面端发来的工具大致有两类：

- 普通函数工具：参数是规整的 JSON，比如 `{"path":"/tmp/a.txt"}`；
- 自由文本工具：参数可能是一大段 shell 脚本或补丁文本。

`exec` 和 `apply_patch` 属于后一种。桌面端把它们叫作 `custom` 工具，上游却更熟悉普通的 `function` 工具。

这就像一边要的是一张填好的表格，另一边递过来的却是一封自由格式的信。两边说的是同一件事，可程序按格式检查时会直接拒收。

我的解决方法是来回包两次。发给上游前，先把自由文本装进一个名为 `input` 的 JSON 字段：

~~~json
{
  "name": "exec",
  "arguments": {
    "input": "完整的命令或脚本"
  }
}
~~~

上游返回后，桥接再把 `input` 里的文字拿出来，还原成桌面端想要的格式。

桌面端还会把一组工具放在同一个分组里，类似文件夹。上游有时会把 `exec` 回成 `functions.exec`。对人来说一看就知道是同一个工具，程序却会认为它们是两个名字。桥接也要把这类前缀去掉。

## 第三个问题：上一次命令只记了开头，没记结果

前面的转换做完后，新对话已经可以调用工具，但某些旧对话还是会报：

~~~text
No tool output found for tool call call_xxx.
~~~

用大白话翻译就是：“我看到你发起了 `call_xxx`，但没找到它的执行结果。”

工具调用一般有一个 `call_id`，就像快递单号。发起工具调用时带着这个号，交回执行结果时也要带同一个号，上游才知道结果属于哪次调用。

如果用户恰好在命令执行中断掉对话，历史里就可能只有“我要调用工具”，没有“这是执行结果”。下一次只要继续这个对话，整段历史都会再次发给上游。上游检查到这笔“有去无回”的记录后就拒绝处理。所以即使当前只说了一句“继续”，也可能立即报错。

桥接在转发请求前，现在会先整理一遍历史：

- 每次调用后面放它自己的结果；
- 同一个 `call_id` 重复了，只保留一组；
- 只有结果、找不到对应调用的记录丢掉；
- 只有调用、没有结果的中断记录，补一条“本次调用当时未完成”。

最后一条不能补成假的“执行成功”。如果命令实际没跑，却告诉模型已经成功，后面的判断都会建立在假结果上。

## 第四个问题：思考模式还需要上一轮记录

另一个常见报错是：

~~~text
The `reasoning_text` in the thinking mode must be passed back to the API.
~~~

意思是：在思考模式下，对话进入下一轮时，上游要求把前一轮与工具调用相关的 `reasoning` 记录一起带回来。经过多层中转后，某些旧历史只保留了工具调用，这部分记录却丢了。

已经丢失的内容不可能凭空找回。所以我只在“这一段历史有工具调用，但没有任何 reasoning 记录”时，补上一条清楚的占位说明：这次思考记录没有保存在对话里。

这不是伪造模型的思考内容，只是补齐上游强制要求的格式。正常保留完整的新对话不会被改动。

## 为什么还要在报错后再试一次

按道理说，请求发出前已经整理过历史，应该不会再有配对错误。但请求还要经过 new-api 和上游的再次转换，边界情况下仍然可能被拒绝。

因此桥接还做了一个很保守的重试：只有当上游明确说某个 `call_id` 缺少调用结果，或者某个结果找不到调用时，才针对这一个 ID 修好后再发一次。

鉴权失败、余额不足、模型不存在等错误不会重试。不区分原因地反复重试，只会让报错更慢，还可能重复计费。

## 桥接程序放在哪里

我没有让每台客户端都装一份修复脚本，而是把它放在服务器上。这样新电脑安装好客户端后，仍然只需配置 new-api 地址和密钥。

nginx 把 `/v1/responses` 请求交给桥接，桥接处理后再转给 new-api；其他页面和管理接口仍然直接走 new-api。

~~~nginx
location = /v1/responses {
    proxy_pass http://127.0.0.1:3011;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_read_timeout 600s;
}

location / {
    proxy_pass http://127.0.0.1:3000;
}
~~~

桥接只监听服务器本机地址，不直接开放到公网。systemd 负责开机启动，程序异常退出后也会自动拉起。

~~~ini
[Service]
Environment=REWRITE_PORT=3011
Environment=REWRITE_UPSTREAM=http://127.0.0.1:3000
ExecStart=/usr/bin/python3 /opt/tools-bridge/rewrite_proxy_v2.py
Restart=always
RestartSec=2s
~~~

## 调试时还把服务器内存撑爆了

为了弄清 Windows 客户端到底发了什么，我曾临时开启完整请求抓取。每次请求都会保存三份大数据：客户端发来的原文、桥接修改后的内容、上游返回的完整响应。

当时有一次对话已经超过 13 万 token。服务器只有约 1.7 GiB 内存，还没有 swap。长请求、JSON 解析、抓包和 new-api 自己的缓存叠在一起，最后 SSH 和 HTTPS 都无法正常握手，只能强制重启服务器。

重启后我做了这几项保护：

- 关闭完整抓包，删除包含对话和提示词的临时文件；
- 增加 4 GiB swap，让瞬间的内存高峰有一个缓冲；
- 限制桥接最多使用 384 MiB 内存；
- 限制 new-api 最多使用 640 MiB；
- 限制 MySQL 最多使用 512 MiB；
- 让这些服务超限时单独重启，不再拖死整台服务器。

swap 只是应急垫，速度比内存慢得多。如果请求量一直很大，正确的方法还是升级服务器内存，不能指望加 swap 代替扩容。

## 怎么确认已经修好

只在对话框里问一句“你好”没有用。这只能证明密钥有效，模型能返回文字。

我先用自动化测试覆盖各种故障历史：调用和结果顺序颠倒、重复的 `call_id`、只有调用没有结果、只有结果没有调用、缺失 reasoning，以及 DSML 被拆成多段返回等。当前基础协议转换 19 项、历史修复 10 项、报错后定向重试 1 项，均已通过。

然后再用真实客户端完成一组实际操作：

1. 让 Agent 查看当前目录；
2. 让它搜索代码；
3. 用 patch 新建或修改一个文件；
4. 再读取文件，确认真的修改成功；
5. 在同一个对话里连续调用多次工具；
6. 中断一次操作，再继续原对话。

这些全部通过，才能说它真的可以给 Agent 使用。

## 这套方案不能解决什么

桥接只是翻译已知的格式差异，不会让模型凭空获得原本没有的能力。

如果上游根本不会调用工具，桥接也没法替它决定该用什么工具。如果客户端以后增加新格式，桥接也需要更新。上游不支持的网页搜索等功能，也不是修改一个名字就能做出来的。

另外，new-api 中的模型名只是路由别名。它可以方便客户端调用和渠道切换，但不会把上游模型变成另一个模型。协议兼容了，也不等于速度、能力和原生服务完全一样。

## 总结

这次最大的误区，就是看到模型能聊天，就以为“OpenAI 兼容接口”已经完全兼容了桌面 Agent。

聊天只需要传文字。Agent 还要正确传递工具名、参数、调用编号、执行结果和上一轮历史。其中任何一环格式不对，都会出现“聊天正常，工具全坏”的现象。

我加的桥接本质上就做三件事：

~~~text
发出前：把客户端的工具格式翻译给上游
返回时：把上游的工具格式翻译回客户端
继续对话时：修好历史中断掉的调用和结果
~~~

做完这些，OpenCode Go 的 DeepSeek Flash 才不只是经 new-api “能回话”，而是可以真正跟着桌面 Agent 读文件、跑命令和改代码。
